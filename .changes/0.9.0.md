## 0.9.0 - 2026-11-20

This release targets the Dagger `v1.0.0-beta.27` API view and runs on stock `v1.0.0-beta.27` engines and on later 1.x engines that serve that view. Applications depend on `tokeira-dagger-sdk = "0.9.0"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.9.0`.

### Added
- A Cargo package that is not a module calls a Dagger module through a typed client. `dagger module client add <module>`, run in the package's directory, records the module in the workspace's `dagger.toml` and generates `src/dagger_clients/<module>/`; the author writes `mod dagger_clients;` once, and generation never edits authored source. `greeter::Client::new(&client)` takes the package's `dagger_sdk::Client` and sends nothing. It has the module's constructor, `greeter()` and `greeter_opts(&greeter::QueryGreeterOpts::default().with_greeting("hi"))`, with `r#ref` and `load` for the module's handles and Core's, in the calling convention of a module's dependencies. The session has the engine serve the module once, before the first request made through the client. A client generated for a function the module no longer has fails with `generated client for "<address>" is out of date; regenerate it`, a `QueryError::ModuleClient`, which is a new variant. Generation sets the package's dependency on `tokeira-dagger-sdk` to exactly the release, or the commit, the runtime is installed from, keeps the dependency's key and other fields, and leaves `Cargo.lock` alone; a dependency inherited from a Cargo workspace must already state that release. Each generated directory has a `.dagger-generated.json` that records its files: `dagger generate` refuses to overwrite a generated file that was edited, with `<path> contains user changes; refusing to overwrite it`, and writes nothing, and `dagger module client rm` removes a client's unchanged files. The generated code passes the package's own `cargo fmt --check` and `cargo clippy -- -D warnings`. The [module clients guide](https://github.com/tokeira/dagger-rust-sdk/blob/main/docs/client-generation.md) describes the calls, what generation writes, and what it refuses by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61
- A module gets its dependencies through `dagger module client add`. Run in the module's directory, `dagger module client add ../greeter` records `greeter` as a client of the module in the workspace's `dagger.toml`, writes it as a `[[dependencies]]` table in the module's `dagger-module.toml`, and regenerates the module, which calls it through `context.query().greeter()` as in 0.8.0. A module in the workspace is written with its path from the module's directory and any other with its Git reference, without a pin, under the name of its module; the tables are ordered by those names, and the rest of the file is kept as it is written, comments included. `dagger module client rm` removes the dependency: generation removes its table and its unchanged generated bindings; an edited binding stays, and generation no longer tracks it. Generation refuses two clients whose modules have one name. The runtime no longer refuses a module that has clients by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61

### Changed
- A module's dependencies are exactly the clients recorded for it. `dagger generate` rewrites the `[[dependencies]]` tables of the module's `dagger-module.toml` from the clients in the workspace's `dagger.toml`, so a dependency written by hand that is not a client is removed, and the changes `dagger generate` shows before applying them include the removal. Before regenerating a 0.8.0 module with this release, run `dagger module client add <source>` once for each dependency its `dagger-module.toml` states, with the `source` the table states. A table that is then a client keeps its name and other settings, and loses its `pin`; `dagger.lock` holds the commit of a Git reference. A module configured by `dagger.json` alone regenerates as before while it has no dependencies and no clients; with either, generation fails before writing anything and advises `dagger module migrate` with the module's path from the workspace root, such as `dagger module migrate /.dagger/modules/gate`, which moves the configuration to `dagger-module.toml` and records its dependencies as clients, then `dagger generate`; a coding agent passes `-y` to apply each, or `--no-apply` to preview the migration. `dagger module client add` in such a module, which the engine takes for a Cargo package until the module is migrated, fails the same way before writing anything, and the advice ends with `dagger module client add` again, run from the directory that holds `dagger.json`. A new module's `dagger-module.toml` is written without indentation by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61
- `dagger generate` treats a module's generated files as Dagger's Go SDK treats the files it records, with the module's `.dagger/rust/operation-manifest.json` as the record. A deleted generated file is written again, where 0.8.0 refused with `previously owned artifact is missing or not regular`. An edited file that generation would rewrite is refused with `<path> contains user changes; refusing to overwrite it`, and nothing is written; 0.8.0 refused it with `previously owned artifact digest is stale`. An edited file that generation no longer writes, such as a binding of a removed dependency, is kept and no longer recorded, and generation carries on, where 0.8.0 refused with the same message. A file the manifest does not record is replaced when it begins with `// @generated`, and adopted when it already holds the generated bytes, where 0.8.0 refused either. An unchanged file that generation no longer writes is now removed from the workspace, where 0.8.0 left it there by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61

### Removed
- The runtime's `generateClient` and `requiredClientGenerationFiles` functions are removed, with the generator behind them, which wrote one Cargo library for each client. No command of a Dagger `v1.0.0-beta.27` engine reached them: `dagger module client add` generates through `generateScope`, which now writes a package's clients and a module's dependencies. An engine that still asks the runtime for a client through `generateClient` reports that the SDK does not support client generation by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61
