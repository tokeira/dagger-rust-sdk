## 0.7.1 - 2026-11-16

This release targets the Dagger `v1.0.0-beta.27` API view and runs on stock `v1.0.0-beta.27` engines and on later 1.x engines that serve that view. Applications depend on `tokeira-dagger-sdk = "0.7.1"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.7.1`.

### Fixed
- A module with an object that keeps no state builds without warnings from its generated code. For such an object, with no `#[dagger(field)]` and no other field the engine keeps, the generated `module_codec.rs` bound an `object` and a `context` that it did not use and declared a map `mut` that it never changed, so every build of the module warned of unused variables and an unneeded `mut`, and the expansion of `#[dagger_sdk::object]` failed Clippy's `unused_unit`. The generated codec now names only what it uses, and the expansion returns the unit without writing it out by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/54
- Generation no longer fails for a module whose dependency gives an argument a default path, ignore patterns or a default address, sets a function's cache policy, marks a function as an agent or for `dagger up`, or exports a collection. The engine describes these on the dependency's functions, arguments and types with its module-authoring directives: `@defaultPath`, `@ignorePatterns`, `@defaultAddress`, `@cache`, `@agent`, `@up`, `@collection`, `@keys`, `@get` and `@delta`. 0.7.0 refused every use of them, so `dagger generate` failed with `TARGET_INACTIVE_DIRECTIVE_CHANGED` at the dependency's coordinate, such as `Greeter.entries(source:)`, and the module could not load. The directives tell the engine how to fill in or schedule the dependency's function and change nothing that a caller sends, so they are now accepted on a dependency's coordinates. On a coordinate of the SDK's reviewed Core API they are still refused by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/54
- A module that depends on another module compiles when its `Cargo.toml` keys the SDK dependency under a name other than `dagger_sdk`. The bindings generated for the dependency's types named `dagger_sdk::` whatever the module called the SDK, so the module's build could not resolve `dagger_sdk`. The bindings now reach the SDK under the module's name for it, as the rest of the module's generated code does by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/54
