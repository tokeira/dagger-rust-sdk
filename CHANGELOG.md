## 0.9.0 - 2026-11-20

This release targets the Dagger `v1.0.0-beta.27` API view and runs on stock `v1.0.0-beta.27` engines and on later 1.x engines that serve that view. Applications depend on `tokeira-dagger-sdk = "0.9.0"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.9.0`.

### Added
- A Cargo package that is not a module calls a Dagger module through a typed client. `dagger module client add <module>`, run in the package's directory, records the module in the workspace's `dagger.toml` and generates `src/dagger_clients/<module>/`; the author writes `mod dagger_clients;` once, and generation never edits authored source. `greeter::Client::new(&client)` takes the package's `dagger_sdk::Client` and sends nothing. It has the module's constructor, `greeter()` and `greeter_opts(&greeter::QueryGreeterOpts::default().with_greeting("hi"))`, with `r#ref` and `load` for the module's handles and Core's, in the calling convention of a module's dependencies. The session has the engine serve the module once, before the first request made through the client. A client generated for a function the module no longer has fails with `generated client for "<address>" is out of date; regenerate it`, a `QueryError::ModuleClient`, which is a new variant. Generation sets the package's dependency on `tokeira-dagger-sdk` to exactly the release, or the commit, the runtime is installed from, keeps the dependency's key and other fields, and leaves `Cargo.lock` alone; a dependency inherited from a Cargo workspace must already state that release. Each generated directory has a `.dagger-generated.json` that records its files: `dagger generate` refuses to overwrite a generated file that was edited, with `<path> contains user changes; refusing to overwrite it`, and writes nothing, and `dagger module client rm` removes a client's unchanged files. The generated code passes the package's own `cargo fmt --check` and `cargo clippy -- -D warnings`. The [module clients guide](https://github.com/tokeira/dagger-rust-sdk/blob/main/docs/client-generation.md) describes the calls, what generation writes, and what it refuses by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61
- A module gets its dependencies through `dagger module client add`. Run in the module's directory, `dagger module client add ../greeter` records `greeter` as a client of the module in the workspace's `dagger.toml`, writes it as a `[[dependencies]]` table in the module's `dagger-module.toml`, and regenerates the module, which calls it through `context.query().greeter()` as in 0.8.0. A module in the workspace is written with its path from the module's directory and any other with its Git reference, without a pin, under the name of its module; the tables are ordered by those names, and the rest of the file is kept as it is written, comments included. `dagger module client rm` removes the dependency: generation removes its table and its unchanged generated bindings; an edited binding stays, and generation no longer tracks it. Generation refuses two clients whose modules have one name. The runtime no longer refuses a module that has clients by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61

### Changed
- A module's dependencies are exactly the clients recorded for it. `dagger generate` rewrites the `[[dependencies]]` tables of the module's `dagger-module.toml` from the clients in the workspace's `dagger.toml`, so a dependency written by hand that is not a client is removed, and the changes `dagger generate` shows before applying them include the removal. Before regenerating a 0.8.0 module with this release, run `dagger module client add <source>` once for each dependency its `dagger-module.toml` states, with the `source` the table states. A table that is then a client keeps its name and other settings, and loses its `pin`; `dagger.lock` holds the commit of a Git reference. A module configured by `dagger.json` alone regenerates as before while it has no dependencies and no clients; with either, generation fails before writing anything and advises `dagger module migrate` with the module's path from the workspace root, such as `dagger module migrate /.dagger/modules/gate`, which moves the configuration to `dagger-module.toml` and records its dependencies as clients, then `dagger generate`; a coding agent passes `-y` to apply each, or `--no-apply` to preview the migration. `dagger module client add` in such a module, which the engine takes for a Cargo package until the module is migrated, fails the same way before writing anything, and the advice ends with `dagger module client add` again, run from the directory that holds `dagger.json`. A new module's `dagger-module.toml` is written without indentation by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61
- `dagger generate` treats a module's generated files as Dagger's Go SDK treats the files it records, with the module's `.dagger/rust/operation-manifest.json` as the record. A deleted generated file is written again, where 0.8.0 refused with `previously owned artifact is missing or not regular`. An edited file that generation would rewrite is refused with `<path> contains user changes; refusing to overwrite it`, and nothing is written; 0.8.0 refused it with `previously owned artifact digest is stale`. An edited file that generation no longer writes, such as a binding of a removed dependency, is kept and no longer recorded, and generation carries on, where 0.8.0 refused with the same message. A file the manifest does not record is replaced when it begins with `// @generated`, and adopted when it already holds the generated bytes, where 0.8.0 refused either. An unchanged file that generation no longer writes is now removed from the workspace, where 0.8.0 left it there by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61

### Removed
- The runtime's `generateClient` and `requiredClientGenerationFiles` functions are removed, with the generator behind them, which wrote one Cargo library for each client. No command of a Dagger `v1.0.0-beta.27` engine reached them: `dagger module client add` generates through `generateScope`, which now writes a package's clients and a module's dependencies. An engine that still asks the runtime for a client through `generateClient` reports that the SDK does not support client generation by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/61

## 0.8.0 - 2026-11-19

This release targets the Dagger `v1.0.0-beta.27` API view and runs on stock `v1.0.0-beta.27` engines and on later 1.x engines that serve that view. Applications depend on `tokeira-dagger-sdk = "0.8.0"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.8.0`.

### Added
- A module can construct and call the modules it depends on, as a Go module can. For each dependency declared under `[[dependencies]]` in the module's `dagger-module.toml`, `dagger generate` writes typed bindings into the module's `dagger_generated`, in the calling convention of the Core bindings. `context.query().greeter()` constructs the dependency `greeter`, and `greeter_opts(&QueryGreeterOpts::default().with_greeting("hi"))` passes its constructor's optional arguments. A function that returns an object returns a lazy handle; one that returns a value, a nullable object or a list is `async` and returns `Result<T, QueryError>`, which `?` turns into a `ModuleError` with the dependency's message. Optional arguments go in a borrowed options struct with `with_*` setters, passed to an `_opts` method. Required arguments are positional in the alphabetical order of their GraphQL names, as in the Core bindings, not in the order the dependency declares them. A dependency's enum is a Rust enum, and its interface is a trait and a `...Client` handle that the dependency's objects implement and convert to. The Dependencies section of the module authoring guide describes the calls, the names generation changes or refuses, and what is left out compared with Go: a module calling its own functions, a dependency's object behind an interface the module declares, Core's interface traits on a dependency's handles, and `As<Interface>()` by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/58
- An object can keep a dependency's objects and enums in private state. A `#[dagger(state)]` field typed as a dependency's handle or enum, bare or in an `Option` or a `Vec`, is kept by the engine from one call to the next: the handle crosses as its ID and is loaded again on the next call's session. The engine refuses a dependency's type in a module's own API, in an exported function's arguments or result and in a `#[dagger(field)]`, as it does for every SDK. Generation and the build accept such a signature, and the module then fails to load with the engine's reason. A dependency type called `Result`, `Option` or `Vec` is written by its path, `dagger_generated::Result`; the bare name is still the standard type by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/58
- A module loads a dependency's object from an ID as it loads a Core object. `context.query().r#ref::<T>(id)` builds a lazy handle without a request, and `context.query().load::<T>(id).await` first checks that the object exists and has that type. Both accept every type that implements the new `dagger_generated::ModuleLoadable`: Core's handles and the handles of the module's dependencies. There is no `As<Interface>()`: `context.query().r#ref::<GreeterNamedClient>(message.id().await?)` gives a value as an interface it implements, and passes a Core object where a dependency's interface is expected by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/58

### Changed
- The bindings generated for a dependency's types are typed. 0.7.1 bound each object and interface of a dependency as an untyped handle, whose methods took `Json` arguments and returned a `QueryBuilder`, with a public `selection()` and a hidden `from_query`, and bound each enum without its wire names. Those methods, `selection()` and `from_query` are gone; a 0.7.1 module had no way to construct such a handle, so no working call changes. A type outside the Core API the SDK targets that no dependency owns, such as one a later engine adds, keeps the untyped handle. A dependency function that names such a type, as an argument or a result, now fails generation with `SCHEMA_FIELD_UNMAPPED` at the function's coordinate, where 0.7.1 bound the function untyped. Generation also refuses a dependency called `load` or `ref`, and a dependency type that would be bound under a name or in a file of the module's generated support, such as `ModuleContext`, `ModuleQuery` or `ModuleLoadable`, with `RUST_NAME_COLLISION` or `OPERATION_ARTIFACT_COLLISION` at the coordinate; declare the dependency under another `name`. Moving a module to 0.8.0 takes one `dagger generate`, whose changes are committed with the move; until then the module fails to load with `GENERATED_STALE`, as after any SDK release by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/58
- `ModuleQuery::r#ref` and `ModuleQuery::load`, the methods of `context.query()`, take any type that implements `dagger_generated::ModuleLoadable` rather than any `Loadable`. Every Core handle implements it, so a call that loads a Core handle compiles as before. A helper of the module's own that is generic over `T: Loadable` and calls either method needs the bound `T: ModuleLoadable` instead by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/58

### Fixed
- Generation accepts a module dependency that declares an interface. The engine marks every type of a dependency with `@sourceMap`, which names the module that owns the type, and marks the dependency's interfaces too, although the directive's definition does not list interfaces among the places it may appear. 0.7.1 refused such a schema with `SCHEMA_DIRECTIVE_ARGUMENT_INVALID` at the interface, so `dagger generate` failed for a module that depended on a module with an interface, and the module could not load. The directive is now accepted on an interface. Every other directive stays confined to the places its definition lists by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/58
- Generation accepts a module dependency whose object has a field. The engine marks every plain field of a module's object with `@trivialResolveField`, an engine-internal marker that the engine's MCP server reads, and its schema defines no directive of that name. 0.7.1 refused any directive without a definition, so `dagger generate` failed with `SCHEMA_DIRECTIVE_ARGUMENT_INVALID`, "directive application references a missing definition", at the field's coordinate, such as `GreeterMessage.name`, for a module that depended on a module with such an object, and the module could not load. The marker changes nothing that a caller sends or receives, so it is now left out as the engine writes it: on a field, without arguments, in a schema that does not define it. Any other directive without a definition is still refused by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/58

### Dependencies
- The SDK requires `zip` 9.0.5, which carries the fix for RUSTSEC-2026-0548: an archive could show `ZipArchive` one set of entry names and extract under others through `ZipStreamReader`. CLI provisioning reads its archive only through `ZipArchive`, so the advisory does not reach it by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/57

## 0.7.1 - 2026-11-16

This release targets the Dagger `v1.0.0-beta.27` API view and runs on stock `v1.0.0-beta.27` engines and on later 1.x engines that serve that view. Applications depend on `tokeira-dagger-sdk = "0.7.1"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.7.1`.

### Fixed
- A module with an object that keeps no state builds without warnings from its generated code. For such an object, with no `#[dagger(field)]` and no other field the engine keeps, the generated `module_codec.rs` bound an `object` and a `context` that it did not use and declared a map `mut` that it never changed, so every build of the module warned of unused variables and an unneeded `mut`, and the expansion of `#[dagger_sdk::object]` failed Clippy's `unused_unit`. The generated codec now names only what it uses, and the expansion returns the unit without writing it out by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/54
- Generation no longer fails for a module whose dependency gives an argument a default path, ignore patterns or a default address, sets a function's cache policy, marks a function as an agent or for `dagger up`, or exports a collection. The engine describes these on the dependency's functions, arguments and types with its module-authoring directives: `@defaultPath`, `@ignorePatterns`, `@defaultAddress`, `@cache`, `@agent`, `@up`, `@collection`, `@keys`, `@get` and `@delta`. 0.7.0 refused every use of them, so `dagger generate` failed with `TARGET_INACTIVE_DIRECTIVE_CHANGED` at the dependency's coordinate, such as `Greeter.entries(source:)`, and the module could not load. The directives tell the engine how to fill in or schedule the dependency's function and change nothing that a caller sends, so they are now accepted on a dependency's coordinates. On a coordinate of the SDK's reviewed Core API they are still refused by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/54
- A module that depends on another module compiles when its `Cargo.toml` keys the SDK dependency under a name other than `dagger_sdk`. The bindings generated for the dependency's types named `dagger_sdk::` whatever the module called the SDK, so the module's build could not resolve `dagger_sdk`. The bindings now reach the SDK under the module's name for it, as the rest of the module's generated code does by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/54

## 0.7.0 - 2026-11-15

This release targets the Dagger `v1.0.0-beta.27` API view and runs on stock `v1.0.0-beta.27` engines and on later 1.x engines that serve that view. Applications depend on `tokeira-dagger-sdk = "0.7.0"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.7.0`.

### Changed
- The SDK runs on later Dagger engines. It accepts an engine of its target release, `v1.0.0-beta.27`, or of any later 1.x release that serves the `v1.0.0-beta.27` API view, which a module selects with `engineVersion = "v1.0.0-beta.27"` in its `dagger-module.toml` and a client gets from a `v1.0.0-beta.27` CLI. Before a session is used, the SDK asks the engine for its release and for the view it serves. An engine older than the target fails with the new `CompatibilityErrorKind::EngineTooOld`, an engine of another major version with `VersionMismatch`, and another view with the new `ViewMismatch`, whose message says how a module and a client select their view. `allow_unverified_compatibility` still waives only missing evidence, which now includes an engine that states no view (`CompatibilityEvidenceGap::MissingView`). Under `dagger run`, a client's session has the view of the CLI running the command, so that CLI must be `v1.0.0-beta.27` by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/51
- `dagger module init` writes the SDK's target release as the module's `engineVersion`, rather than the engine's release, so a module initialized on a later engine is served the API view that the SDK's bindings are compiled for by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/51
- Code generation accepts a later engine's copy of the target's API view. It compares the copy with the SDK's reviewed Core API by its wire contract: reworded documentation, new deprecations, and fields and optional arguments the SDK does not bind are accepted, while a removed or retyped coordinate, a changed default, a new required argument or input field, or a new enum value is refused. A module's operation manifest records the identity of the schema the SDK consumed rather than the bytes the engine sent, so the module's generated files stay current on such an engine. Moving a module generated by 0.6.0 to 0.7.0 takes one `dagger generate`, whose changes are committed with the move; until then the module fails to load with `GENERATED_STALE`, as after any SDK release. When a module's view is not the target, `dagger generate` tells the user of an engine older than the target to run the module on a newer one, and anyone else which `engineVersion` to declare by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/51

### Fixed
- Generation no longer fails for a module that depends on another module. The engine adds every object type of a module's dependencies to the possible types of Core's `Node` interface, since each has an ID, and 0.6.0 compared each Core interface's possible types with its reviewed Core API in full, so `dagger generate` failed with `SCHEMA_CORE_COORDINATE_INCOMPATIBLE` at `Node`, and the module could not load. Possible types are now compared over Core types only. The module's generated files bind the dependency's types, but a module cannot yet call a dependency or take its objects as arguments by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/51

## 0.6.0 - 2026-11-14

This release targets stock Dagger `v1.0.0-beta.27` engines and CLIs. Applications depend on `tokeira-dagger-sdk = "0.6.0"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.6.0`.

### 🔥 Breaking Changes
- The SDK targets stock Dagger `v1.0.0-beta.27` engines and CLIs instead of `v1.0.0-beta.25`. Each Dagger release serves an API view of its own, and the SDK requires beta.27's, so a module must declare `engineVersion = "v1.0.0-beta.27"` in its `dagger-module.toml`. The generated client follows the beta.27 schema, which writes acronyms in field names as words and drops the legacy `ImageMediaTypes` and `ImageLayerCompression` spellings, so `GitBundle::prerequisite_sh_as` is now `prerequisite_shas`, `Container::experimental_with_all_gp_us` is now `experimental_with_all_gpus`, `ImageMediaTypes::OciMediaTypes` and `DockerMediaTypes` are now `Oci` and `Docker`, and `ImageLayerCompression::EStarGz` is now `Estargz`. The experimental `Query::format_identifiers` and `identifier` move to the `Naming` object that `Query::naming` returns, and `Query::naming_dictionary` becomes `Naming::dictionary`. The client also adds a `resolve_broken_symlinks` option for `Container::directory` and `Directory::directory`, a `key_by_content` option for `File::sync`, a `client_version` option for `ModuleSource::client_schema_introspection_json`, `Directory::with_platform`, and `WorkspaceSdk::scope_setting`. A module that declares beta.27 is named by the engine's new rules, as modules in every SDK are, so its callers may see some names spelled differently: a struct `HttpClient` in a module `tiny` is `TinyHTTPClient` rather than `TinyHttpClient`, and an enum variant `GitHub` is the member `GITHUB` rather than `GIT_HUB`. The module's Rust code does not change by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/48

### Dependencies
- The repository builds resolve `rustix` 1.1.6, which fixes RUSTSEC-2026-0486: its extended-attribute functions could mark unwritten bytes as initialized when given a zero-length buffer. The SDK never reaches those functions. Crates that depend on the SDK resolve their own `rustix` release, and `cargo update -p rustix` moves them to a fixed one by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/48

## 0.4.1 - 2026-11-01

This release targets stock Dagger `v1.0.0-beta.23` engines and CLIs. Applications depend on `tokeira-dagger-sdk = "0.4.1"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.4.1`.

### Added
- A module's arguments, results and fields can be Core enums and scalars, such as `NetworkProtocol`, `Platform`, `Json` and `Bytes`, as a Go module's can. An enum crosses the boundary as the name of its member and accepts the engine's aliases for it, and a scalar keeps its exact text. A default names an enum member, as in `#[dagger(default = NetworkProtocol::Udp)]`, or gives a scalar's text as a string literal, and generation refuses a default that is not one of the enum's members, or a `Json` default that is not JSON text by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/42

### Fixed
- Generation no longer fails for a module whose object field or interface method names a Core type that none of its functions takes or returns, such as `#[dagger(field)] source: Directory`. It failed with "generated module assets could not be rendered" and no location by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/42
- When the engine refuses a module's registration, for example because a function does not have the shape its role requires, the command that loaded the module showed only `Error: Dispatch(Registration(RegistrationError { source_present: true, .. }))`. It now shows the engine's reason by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/42

### Experimental
- A module function with `role = "agent"` is an agent function, as a Go function marked `+agent` is, so `dagger agent` composes the module's expertise into its conversation. The engine checks the function's shape when it loads the module: its one required `Llm` argument is the conversation, and it returns the conversation it extends. The role is experimental, as is Dagger's `Function.withAgent` by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/42

## 0.4.0 - 2026-10-31

This release targets stock Dagger `v1.0.0-beta.23` engines and CLIs. Applications depend on `tokeira-dagger-sdk = "0.4.0"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.4.0`.

### 🔥 Breaking Changes
- The SDK targets stock Dagger `v1.0.0-beta.23` engines and CLIs instead of `v1.0.0-beta.21`. From `v1.0.0-beta.22` each Dagger release serves an API view of its own, and the SDK requires beta.23's, so a module must declare `engineVersion = "v1.0.0-beta.23"` in its `dagger-module.toml`. The generated client follows the beta.23 schema. It adds `File.extract`, `Container.withMountedFiles`, a `sourceDateEpoch` option for `Container.publish`, `Container.export`, `Container.exportImage` and `Container.asTarball`, and a `followSymlinks` option for `Query.sshfsVolume`. It removes `ArtifactResult`, `Artifacts.values`, `Artifacts.withArtifacts` and `CollectionTypeDef.batchType`, which beta.23 drops without deprecation by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/38

### Added
- A module is described by its crate root's `//!` documentation, as a Go module is by its package documentation: the first line is the module's short description and the rest its long description. The `src/lib.rs` that `dagger module init` writes starts with a placeholder for the module's description by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/39

### Changed
- A new CLI session announces the SDK's target release with `dagger session --version`, as Dagger's Go SDK does from `v1.0.0-beta.22`, so the engine serves the API view the generated client was built for even when the session runs a CLI of another release, such as the `dagger` on `PATH` that the SDK falls back to. `ClientConfigBuilder::version` still overrides the announced release by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/38
- A module whose `engineVersion` selects another API view than the SDK's target is refused with a message that names the view the engine served and the `engineVersion` to declare, and the module authoring guide describes how to move a module to a new SDK release by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/38
- A handle made from an ID that a query returned, such as the result of `sync` or an element of a list of objects, keeps that ID, so passing it as an argument no longer asks the engine for its ID first, as Dagger's Go SDK does from `v1.0.0-beta.22`. As in the Go SDK, a handle that a module function receives still asks for its ID by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/39

## 0.1.0 - 2026-10-19

This release targets stock Dagger `v1.0.0-beta.18` engines and CLIs. Applications depend on `tokeira-dagger-sdk = "0.1.0"` from crates.io, which brings `tokeira-dagger-sdk-macros` at the same version, and modules install the runtime from `github.com/tokeira/dagger-rust-sdk/runtime@v0.1.0`.

### 🔥 Breaking Changes
- The SDK targets stock Dagger `v1.0.0-beta.18` engines and CLIs instead of the fork's `v1.0.0-beta.11.rust.N` builds, and its compiled CLI downloads from dl.dagger.io. The generated client follows the beta.18 schema. It adds types such as `AgentMessage`, `Artifact`, `GitRemote` and the `Bytes` scalar, and drops those beta.18 removed, including `CurrentModule.asSDK`, `AgentGroup`, `CheckGroup`, `GeneratorGroup` and `UpGroup` by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/3
- Module clients and module dependencies are not generated yet. A scope that records them is refused before anything is written, until the SDK defines Rust clients for beta.18's client scopes by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/4
- The SDK is published as `tokeira-dagger-sdk`, with the `tokeira-dagger-sdk-macros` companion, and its versions start at `0.1.0`. Code still names the crate `dagger_sdk`, so a project changes only its `Cargo.toml` dependency. Generated projects record it as `dagger-sdk = { package = "tokeira-dagger-sdk", … }` by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/5

### Added
- The runtime installs on stock Dagger engines as an SDK module, with `dagger install github.com/tokeira/dagger-rust-sdk/runtime@<ref>`. `dagger module init rust` scaffolds a Rust module and writes its `dagger-module.toml`, and `dagger generate` regenerates it. The runtime builds its SDK content from the commit pinned in `runtime/assets/sdk-dependency.json`, so no engine has to package it by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/4

### Changed
- Modules the runtime initializes now depend on the renamed package, as `dagger-sdk = { package = "tokeira-dagger-sdk", git = "https://github.com/tokeira/dagger-rust-sdk", rev = … }`, at a commit with the new name. The SDK content the runtime builds carries NOTICE beside LICENSE by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/8
- The SDK needs Rust 1.99.1, up from 1.97.1. Its minimum supported Rust version, the toolchain that generated projects pin, and the image the runtime builds modules with all move to 1.99.1 by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/19

### Fixed
- Void results decode from stock Dagger engines, which return either `null` or an empty object; any other shape is still refused by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/3
- Generated module files are the same on every engine platform. Their generator identity named the tools' platform-specific executables, so files generated on an arm64 engine were stale on amd64, and `dagger generate` and the staleness check there failed with `OPERATION_MANIFEST_STALE`. Regeneration after a runtime upgrade, which changes the generator and SDK dependency, now replaces the files the prior manifest owns instead of refusing by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/12
- The `src/lib.rs` that `dagger module init rust` writes is rustfmt-formatted. Its template lost every indent by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/13
- Generated module code compiles without warnings under `-D warnings`, so a module no longer needs lint exceptions for it. Dispatch tripped `clippy::get_first`, the codec of an enum with a deprecated variant tripped `deprecated`, registration of an enum tripped `unused_mut`, and a custom scalar left an unused definition by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/13
- A module function that returns a failed query with `?` reports the engine's error. An execution failure keeps the engine's message, whose trace origin lets the CLI show the failed command and its output, and its command, exit code and output as details, where they fit. An argument that failed to resolve reports the engine's error behind it, and a request failure names its SDK causes, such as "the engine transport failed". Before, these read only "the engine execution failed", "the GraphQL query could not be built" and "the GraphQL query request failed" by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/14
- `dagger module init rust` inside a Cargo workspace that neither lists nor excludes the new module now says so, and names the path to add to that workspace's `exclude` or `members`. It reported only "Cargo dependency resolution failed" by @iw in https://github.com/tokeira/dagger-rust-sdk/pull/14
